### 五个重点的核对结果

- **信号目标与已退出子进程。** 非 shell 分支仍只用本 Session 持有的直接 child PID，唯一变化是 INT → HUP；没有按名称发信号、对整个 paddock 进程组发信号或调用 corral stop。portable-pty 的 Unix child 是 `std::process::Child`，启动时 `setsid`，不是 paddock 自己的会话。`interrupt` 先 `poll_exit`；已回收的 child 由 `exited` 短路，未回收的直接子进程保留 PID，代码中没有另一个全局回收者，未发现新增的直接 PID 复用窗口。shell 仍沿用原来的 shell/前台作业 PGID 收集与 SIGHUP/SIGKILL 路径；缓存 PGID 不等同于永久进程身份，本次没有做 PID 回卷/极端复用实验，不能把直接 child 的结论扩成“任意时间的缓存 PGID 都绝对不会复用”的保证。
- **收集范围。** `self.panes` 包含当前机器全部标签的窗格，`seats.parked` 包含其余已就座机器；没有只取 active tab。每个 TerminalView 同时 take `direct` 与 `viewer.session`。切 agent 时尚在停止的旧 session 仍在 `viewer.session`，也会收进来。`Viewer::spawning` 的 JoinHandle 没有被收入向量，但 `cancel_pending` 取消检查，`Viewer::drop` 把 join 和返回 Session 的 drop 放在后台；已经 close/retire_direct 的 session 也早已发信号、交后台释放。切机器是 UI 线程上的同步交换，不会在交换一半时插入本退出回调。隐藏/移除机器时先逐个 `view.close`，留下的是后台回收或保存的布局，不是漏在 UI 上的活 session。`queued_shell` 只有启动参数，还没有 PTY。
- **退出顺序和剩余依赖。** `windows::quit` 先完成确认、保存布局，再 `cx.quit`；取消确认不会进入 shutdown。GPUI macOS 的 `quit` 经主队列调用 AppKit terminate，平台 `will_terminate` 进入 `App::shutdown`；普通 Dock 退出/注销也通过该正常终止回调，不包括强制结束进程。`App::shutdown` 同步调用 quit observers 后才 clear windows，所以此时 window handle 能访问，take 后剩余 view drop 不再逐个等 live session。代码没有依赖取走后的 session 的窗口析构保存钩子。ctl 的 UI 处理与退出在同一线程，这段同步回调期间不会再执行窗格操作；之后才关闭 ctl server，与其既有后台 transport 回收一致。通常 PTY 等待约为一个 3 秒宽限期加回收开销；整个退出没有由本改动建立的严格有限上界，见建议 2。
- **既有行为。** shell 分支未改，前台作业组的单元测试和集成测试通过。关闭单窗格、标签、切 agent 都继续用原来的关闭/切换路径，非 shell 自然一起改为 HUP，符合本任务明文范围；`Launch::Command` 若只处理 INT、不处理 HUP，其结束方式会变，但这正是已批准的“关终端就是挂断”。本地 attach 的直接信号目标不是 agent；远程对应本机的 `ssh -tt -e none` 子进程，不是远端 agent PID。未运行真实 corral 或 SSH；本地真实 attach 的表现依据任务中主控已有实测，远程这里只核对 argv、所有权和假 ssh/attach 回归。现有 `agent-alive` 文件断言不能单独证明真实 agent 进程存活，因此不把它当作真实 agent 存活实测。
- **新测试的有效性和时序敏感度。** `ready` 在 trap 安装后才输出，等待 ready 后才开始计时，避免把启动开销算进退出。忽略 INT 的测试针对错信号；额外忽略 HUP 的三窗格测试才独立约束宽限期重叠，能区分约 3 秒和约 9 秒。已退出、shell 前台组、单窗格 SIGKILL 兜底都有检查。小于 1 秒和 3～5 秒断言仍受系统停顿/严重抢占影响，不能保证重载下绝不偶发失败；现有余量和明确的性能验收对应，建议保留，不为消除理论上的抖动放宽断言。开发记录中的 RED（3.013 秒、9.040 秒）本轮只核对记录与测试机制，没有在只读审查中改回源码重跑。
