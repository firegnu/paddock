# 任务：各仓库主控之上要不要再有一个 agent（像 Amp 的 Puck）

草稿（2026-10-11，paddock/main 记）。还在讨论，没有批准任何方案，没建任何东西。下面除「用户定了的」之外都是主控的建议。
依据：用户 10-11：“AMP有一个所有主控agent再之上的agent叫什么pock，其实这个还有点意思。”主控一开始把这件事和 P5-83（远景想法放哪）捆在一起说，用户：“等等，我理解先爱咱们在讨论两个事情。对不对？”“把这两件事情先建立两个draft task，并现在里面写出上面咱们讨论的内容”。两件事分开定，本件不依赖 P5-83。

## 现在的用法
用户 10-11：“现在paddock，其实我主要就是和各个repo的主控agent聊，具体的委派主控会自己控制。”每个仓库一个主控（`<仓库>/main`），派谁、怎么审、什么时候合并由主控定；跨仓库的事现在靠用户自己在几个主控之间传话，或让一个主控兼管另一个仓库（paddock 的主控兼管 ranch，也直接在 cairn 仓库干过活）。

## Puck 是什么（主控 10-11 查的）
用户说的是 Amp 的 Puck，2026-07 发布，官方标为实验。它自己不写代码，负责启动别的 agent、盯着它们、给它们发后续指令、找回和归档旧对话、建新项目；在网页、TUI 的命令面板和 Slack 里都能叫出来。
- https://ampcode.com/docs/puck
- https://ampcode.com/news/meet-puck

## 主控的建议（用户没逐条表态）

### 和 Puck 不一样的地方
Puck 直接管一堆临时 agent。这边每个仓库已经有主控、任务文件和审查流程，所以这个 agent（暂且叫总控）应该比 Puck 薄，只做三件事：
- 总览：只读地看各仓库的 `corral ls`、HANDOFF、任务文件，回答“各处在干什么、谁在等我”。
- 转交：跨仓库的事、还没归属的想法，写成需求送到对的仓库的主控（一开始经用户的手）。
- 陪用户想跨仓库的事。如果有 P5-83 的想法仓库，它平时大部分时间是陪用户想、查资料、记下来。

### 边界
- 不替用户批准任何事；转述照抄用户原话。
- 不越过主控去指挥派出去的 agent；不写代码。
- 别的仓库只读；corral 只用 `ls`、`status`、`reply`，不 `send`、不 `stop`（放开之前）。
- 单个仓库里的事，用户照旧直接找那个仓库的主控。

### 代价
多一层转述：话会走样，也会变慢。只有跨仓库的事和还没归属的想法值得过这一手。

### 要不要现在做
用户说的是“有点意思”，不是现在就缺。主控倾向先做 P5-83，用起来之后再看这件要不要。

## 开工前要定
- 要不要做；什么时候做。
- 它住在哪个目录：P5-83 的想法仓库里（主控最初的提议），还是别处。它需要一个不属于任何代码仓库的地方，这是和 P5-83 唯一重叠的一点。
- 用哪家 agent、叫什么名字、怎么启动；它的职责和边界写在哪（它自己目录里的说明，还是做成 ranch 里的一个技能，像 `corral-dispatch` 那样）。
- 什么时候、凭什么放开让它直接给主控发消息。
- paddock 里要不要给它一个固定位置（和 P5-83 的固定位置是不是同一块）。
- 落点：角色约定多半在 ranch 或它自己的目录里，paddock 的代码活只有“显示”那一小块。拆开后各自归哪个仓库。

## 不做（现在）
- 不建目录、不开这个 agent、不改 ranch 和 paddock：等用户定了上面几项。

## 10-11 续：不和 pasture 绑定
P5-83 收尾、pasture 建好之后，用户：“先谈 P5-84 吧”。主控的看法：Puck 的本事这边大半已经有了（派活归各仓库主控；总览有左侧栏、提醒列表和 P5-85 的看板切仓库；陪着想有 `pasture/main`），缺的只剩“跨仓库的事谁来起草、谁记着”；建议不新建东西，让 `pasture/main` 兼这个角色试一两周。

用户：“不，我不想和pasture绑定。”

- **定了**：这个 agent 不住在 pasture 里，不由 `pasture/main` 兼，角色的约定也不写进 pasture。上面「开工前要定」里“住在 P5-83 的想法仓库里”这个选项作废。
- 主控改提的做法（用户还没表态）：角色约定做成 ranch 里的一个技能（像 `corral-dispatch` 那样，跟着 ranch 走，和任何一个仓库都不绑）；agent 要用的时候再开、不常驻；一开始只读加起草；paddock 先不改，它在左侧栏里和别的 agent 一样显示。
- 还没答的：总览、转交、陪着想三样里，用户现在真缺哪样。

## 10-11 续：用户想要的是“副研发经理”
用户：“我现在的工作方式类似这样，我是一个研发经理，下面有一堆leader每一个leader会根据自己手上的活派发给下面的程序员，但是我管理这堆leader也会影响我的注意力，我的意思是有一个类似我下面再加一个角色类似副研发经理，我只需要和副研发经理沟通，leader转去去和副研发经理沟通。副研发经理汇报给我。你觉得如何？还是说这种想法看着挺好，但是实际上并不怎么样。”

这比上面的“只读加起草”走得远：leader 的话都经它，它要能给各主控发消息，还得能替用户答一部分。

主控的看法（建议，用户还没表态）：
- 要解决的问题是真的：注意力被几个主控分掉。
- “所有话都经副手”这个完整版多半不好用，三个原因：
  1. 最值钱的是用户的纠正，而副手分不出哪次该纠正。10-11 这一天用户否了主控三次（标签用下划线、paddock 里固定一个“家”、让 `pasture/main` 兼任），副手手里没有那些理由，多半会放行。
  2. 批准成了二手的。现在的规矩是验收照抄用户原话、建议不当批准；中间多一个会转述的角色，“用户同意了”就不再可靠。
  3. 要用户亲眼看的省不掉（样稿、重开看效果、进不进公开仓库），这类事还是得回到那个主控的窗口。
- 人的副手值钱在跟久了知道老板要什么；agent 没有这个，它知道的只有写下来的规矩。而写下来的规矩可以直接给各主控，不用多一层。
- 主控建议的薄版本，分三样，互相独立：
  1. 收件箱：一个只读的 agent，把“谁在等你、等什么、哪些一句话能答、哪些要你亲自看”排成一张单子。
  2. 原话转达：用户在它那里答一句，它把原话原样送给对应的主控，不改写、不替答。
  3. 从源头少问：给各主控写一条常设的授权（哪几类事照主控建议做、事后汇总；哪几类必须问）。10-11 这一天用户说了约八次“按你的建议来”，这类可以不用问。

## 10-11 续：注意力花在哪
主控问注意力主要花在哪（问题太多、来回切窗口、还是得自己记着谁在等），用户：“我的注意力主要是来回在各个主控之间切看消息。”

主控据此改了建议（用户还没表态）：这件事不用 agent 做，做成 paddock 自己的一个界面——收件箱。
- 现在：左侧栏铃铛（Attention）只列出谁在等、谁有新回复，点一行就跳到那个 agent 的窗格，“切过去看”正是这一步。
- 收件箱：各主控最新的一条回复原文排在一处（等用户的在前），不用切窗格就能读；每条下面能直接回一句，paddock 用 `corral send` 把用户打的字送给那个 agent。
- 为什么不用 agent：界面显示的是原文，不转述、不走样、不花额度，也不多一层；agent 做的摘要用户还是得回头看原文才敢答。
- 限度：corral 的公开命令只给每个 agent 最后一条回复，来回长谈、看样稿仍要进那个窗格；弹着权限框或提问框的回不了，只给一个跳过去的按钮。
- 读过代码：paddock 已经在调 `corral reply`（`app/src/corral.rs`），还没有调过 `corral send`；Attention 当初定的是“不替它回答”，收件箱里是用户自己答，不冲突，但这是 paddock 第一次替用户往 agent 里送话（P5-54 也要用到）。
- 这样 P5-84 就不再是“主控之上的 agent”，而是 paddock 的一个界面功能；“副研发经理”不做。从源头少问（常设授权）仍可单独做。
