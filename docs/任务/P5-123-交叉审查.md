### R1 · 必须改：编辑按原始表的第一个同名项定位，可能改错或删错条目

- **具体触发输入**（合成示例）：

  ```toml
  [[machines]]
  name = "gpu"
  ssh = "old-host"
  label = 7

  [[machines]]
  name = "gpu"
  ssh = "current-host"
  ```

  按上述代码，页面只显示 `current-host`。对它点 Remove，删掉的却是前面被忽略的 `old-host`，`current-host` 仍留在配置里；对它改名，则把前面的 `label = 7` 修成有效字符串，导致 `old-host` 变成生效项、`current-host` 被判重忽略，而运行中的 Link 仍指向原目标。即使两条原来都有效，删除第一条也会让此前被忽略的第二条接替同一个身份。这不是单纯的报错文案问题，而是配置编辑对象有歧义。

### R2-1 · 必须改：等候超时后仍可能先清理、后启动，最后一个使用者结束时没有补清理

- **位置**：`app/src/remote.rs:358–385、404–419、490–494`；关联 `app/src/command.rs:117–127、166–180`、`app/src/viewer.rs:329–353`。
- **已查证事实**：`enter` 在同一把锁里检查并登记，解决了“退休后再登记”的问题；但这把锁不覆盖子进程启动。`idle(CALL)` 满 20 秒后，即使 `uses.running > 0` 也直接返回，随后发唯一一次 `-O exit`。此后的 `leave` 只减计数和通知，退出线程已经结束时不会再清理。普通请求仍在启动子进程之后才检查共同停止标记；attach 在拿到 `Hold` 后另行检查取消、调用 `Session::spawn`。这些操作从登记到真正启动、结束没有被 20 秒的等待上限约束。
- **尚未排除的具体顺序**：请求已经登记，但启动线程迟迟未执行到 `.spawn()`；隐藏机器后，退出线程等满 20 秒，先对旧 socket 发完 `-O exit`；该请求线程随后恢复，仍会启动带 `ControlMaster=auto` 的 ssh，再检查停止标记。attach 同样存在“已通过 viewer 的取消检查、尚未完成 PTY 子进程启动”的窗口。此时取消或丢弃 PTY 仍会收掉本机调用进程，但最后一个 guard 释放后不会再关闭随后才建立的主连接。这是原 R2 的先后顺序问题在超时分支上的残留；触发需要启动阶段拖过等待上限，并非普通请求每次都会发生。本轮依据代码推演，没有做真实 SSH 或调度暂停复现。
- **为什么当前测试不足以排除它**：新增的在途请求测试等 `hung-pid` 出现后才隐藏，证明的是“ssh 已启动且能及时被取消”的路径；它没有覆盖已登记但尚未启动、等候已经超时的路径。“一次请求最多 20 秒”也不能作为证明，因为 `command::spawn` 的 deadline 是子进程启动之后才设置的。
- **改法**：保证该代连接的最后一次清理发生在所有已登记使用者结束之后。可以一直在后台等计数归零；若保留 20 秒时先强制关闭一次的策略，则超时后不能丢掉最终清理责任，应在最后一个使用者释放时再安排该代 socket 的清理。无需阻塞 UI，也无需改变已经正确的新代 socket 方案。补一个把执行卡在登记后、启动前并跨过清理等待上限的假命令／门闩检查，确认迟到操作之后仍有最终清理；不能仅把等待时间加长。完成记录中的“检查和起进程之间没有空档”也应改成准确描述：登记与退休互斥，启动安全依靠登记期间保留最终清理责任。
