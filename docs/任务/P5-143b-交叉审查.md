1. **必须改：默认打开可以把终端输出中的链接变成执行本机程序的入口。** 位置：`app/src/view/links.rs:173–189、378–403`，`app/src/window.rs:2540–2557`。
   - 问题：OSC 8 的显示文字可以是“read documentation”，真正地址却是 `file:///…/run.command`、应用包或 Terminal 配置；`marked()` 无存在性或类型检查，最终直接得到 `open <路径>`。不经 shell 只防止了 shell 字符串解释，不能阻止 LaunchServices 启动应用或执行这类文件。本机 `open(1)` 说明其行为等同于双击文件图标。终端显示的内容可能来自日志、文件、网络或 shell 里的 ssh，不能把“这是本机窗格”当成目标可信。普通路径也走同一入口，只是地址没有被显示文字遮住。探针在 `exists` 一律返回 false 时仍得到 `File("/synthetic/run.command")` 和计划参数 `("open", ["/synthetic/run.command"])`，存在性回调调用次数为 0；没有实际执行它。

3. **必须改：`file://` 丢弃主机名，会打开错误的本机文件；路径解析也混入了 URI 片段。** 位置：`app/src/view/links.rs:178–185、204–225`。

### 建议改

8. **建议改：新启动入口绕过了 P5-126 的进程启动锁。** 位置：`app/src/view/links.rs:399–404`；对照 `app/src/command.rs:18–31`、`docs/DESIGN.md` §4。
   - 问题：直接 `Command::output()` 没经过 `command::start()`。P5-126 已取证过 macOS 的管道创建/CLOEXEC 间隙；这里增加了一个能在间隙启动、也会自行创建管道的入口，长寿命编辑器可能再次持有别的调用的管道或 PTY。探针持有现有 `spawn_guard()` 时，另一个线程的 `links::open("/usr/bin/true", &[])` 仍能完成，确认了绕过；本轮没有复现描述符泄漏本身。现有 512 轮并发回归只用 `command` 入口，所以全绿不能覆盖这里。
   - 改法：显式配置 stdin 为 null、stdout/stderr 为 piped，使用 `command::start()` 启动，释放启动锁后再 `wait_with_output()`；**不能把整段等待放进启动锁**。把这个入口也纳入已有的并发验证，保持原断言和超时。

9. **建议改：`--wait` 命令会长期占用后台执行线程，输出也一直积存在内存。** 位置：`app/src/window.rs:2547–2551`，`app/src/view/links.rs:399–406`。
   - 问题：后台任务里的 `Command::output()` 是阻塞调用。`code --wait` 一类命令直到编辑窗口关闭才返回，这期间占着一个 GPUI 后台执行线程和管道；多次打开会叠加。它不会直接阻塞主线程，因此不按第 2 条的界面卡死判为必须改；但“在后台等”不等于没有资源占用。stdout 目前全部收集后丢掉，stderr 也没有上限。
   - 改法：用独立、可管理的进程等待任务，避免长等待占用共享后台执行资源；不使用的 stdout 丢弃，stderr 限量保留，仍在进程退出时报告非零状态。不应给用户明确设置的 `--wait` 强加几秒超时、杀掉编辑器。补有限时长的假命令测试等待、失败和回收；不用真实编辑器。

### 建议改

3. **建议改：200 ms 超时只结束等待，没有回收 stderr 读取线程。** 位置：`app/src/view/links.rs:703–728`。
   - 问题：`paddock-open-stderr` 一直阻塞 `read()` 到 EOF，没有保存或结束它的机制。启动器已退出、留下的长寿命进程仍持有 stderr 时，`finish()` 虽然返回，读取线程及管道却一直留着；每次打开都可再留一份。这与明确设置 `--wait`、原进程仍在运行的正常等待不同。输出内存已限制为 2000 字节，共用执行器占用也已解决，这里只剩回收边界。

4. **建议改：查询线程创建失败会把该窗格永久留在正在查询状态。** 位置：`app/src/view.rs:1114–1139`，`app/src/view/links.rs:223–253`。
