## 现在是怎样（主控 10-17 记的）
- P5-123 返工 2 时查明的机制：macOS 上 Rust 标准库建管道是先 `pipe`、再分别 `set_cloexec`（P5-123 交叉审查对照本机 Rust 1.96.0 源码 `library/std/src/sys/pipe/unix.rs` 核对过），这两步之间别的线程同时起的子进程会继承这对管道的描述符。继承到写端的子进程活多久，原来那个调用就要等多久才读到 EOF，或者等满超时。
- 当时在测试里用 `lsof` 取证：被故意卡住的假 `ssh -O exit` 拿着新请求输出管道的写端，新请求等满 20 秒报 `timed out waiting on channel`。P5-123 只改了那条测试的夹具避开（`app/tests/remote.rs` 里假 ssh 收到 `-O` 先记一行、测试等它起来再连），产品代码没动。
- 10-17 合并 P5-123 后主控在 main 上复跑：`app/tests/remote.rs` 的 `a_machine_that_hangs_or_fails_never_holds_this_macs_agents_back`（远程机器卡住时本机列表照常每 0.1 秒刷新）在整组远程测试（`cargo test --test remote`）里时过时不过——合并前的 main 8 次失败 3 次，合并后 8 次失败 2 次，单独跑这一条很少失败；当时机器负载 5.5 左右。失败的样子是 3 秒里本机一次刷新都没拿到（`left: 0 right: 5`），或者超过 2 秒。很可能是同一个原因：卡住的假 ssh 继承了本机 `corral ls` 的输出管道。这条是推断，没取证。
- 真实使用里可能的影响（推断，没见到过）：连不上的远程机器那边卡在 `ConnectTimeout` 的 ssh，正好和本机或别的机器的调用同时起时，会把那个调用拖到 ssh 退出或超时。
