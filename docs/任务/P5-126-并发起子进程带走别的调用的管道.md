## 现在是怎样（主控 10-17 记的）
- P5-123 返工 2 时查明的机制：macOS 上 Rust 标准库建管道是先 `pipe`、再分别 `set_cloexec`（P5-123 交叉审查对照本机 Rust 1.96.0 源码 `library/std/src/sys/pipe/unix.rs` 核对过），这两步之间别的线程同时起的子进程会继承这对管道的描述符。继承到写端的子进程活多久，原来那个调用就要等多久才读到 EOF，或者等满超时。

**做了什么**
- `command.rs` 加一把进程内共用的启动锁和 `start` 入口，只锁住描述符准备、`spawn`，返回后立即释放。输入写入、输出读取、等待退出、超时和取消照旧在锁外。
- `agent_shell.rs` 的 passthrough `exec`、托管 agent 启动和回退 attach，`launch.rs` 的登录 shell，全都经过同一把锁；原来的 `output`、`status` 拆为锁内 `spawn`、锁外 `wait_with_output`／`wait`，标准输入输出、环境、工作目录、退出码处理不变。`view/file_drop.rs` 唯一的命令调用在单元测试里，也改走这个入口，避免测试进程内部绕过锁。
- `pty.rs` 从 `openpty` 之前持锁，到 reader/writer 复制、`spawn_command` 返回和 slave 释放之后解锁；后面的终端 I/O、退出处理不动。

**拿主意的地方**
- 采用共用启动锁，不重写标准库/portable-pty 的管道、PTY 或进程管理。macOS 没有当前标准库可用的原子 `pipe2(O_CLOEXEC)` 路径；仅给短命令加锁不够，所有 paddock 启动入口和 PTY 创建都得参加。锁只跨启动阶段，远程进程跑多久不占锁。
- 不在自己的 `pre_exec` 回调里枚举/关闭所有描述符：那还要处理 fork 后的安全限制和标准库用于报告 exec 失败的管道，本次无需增加这层底层实现。
