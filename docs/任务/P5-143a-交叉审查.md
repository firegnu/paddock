### 1. 必须改：颜色查询的结果依赖 PTY 如何分包

- **位置**：`app/src/terminal.rs:62–76`，`Screen::process` 先把整段交给 `parser.advance`，之后才用最终的 `Term::colors()` 回答这一段里的所有 `ColorRequest`。
- **问题**：合法的“设色 → 查询 → 重置 → 查询”若落在同一次 PTY 读取中，第一次查询也会答成重置后的值。连续两次设置不同颜色再分别查询，同样会把两次都答成最后的颜色。PTY 是字节流，程序分开写也不能保证读线程分开读；这不只限于完成记录中说的“真实程序不会这样写”。这是实际的颜色答错，不能作为本任务已知限制放过。
- **复现**：使用当前 worktree 的 `terminal.rs`、`palette.rs` 原文件，经 `rustc` 标准输入编译一个独立检查（产物仅在 `.target/review`，没有修改源码）。依次输入下面四段，比较逐段 `process` 与拼成一段 `process` 的返回值：

  ```rust
  b"\x1b]4;1;rgb:12/34/56\x07"
  b"\x1b]4;1;?\x07"
  b"\x1b]104;1\x07"
  b"\x1b]4;1;?\x07"
  ```

  逐段处理得到 `rgb:1212/3434/5656`、`rgb:cdcd/0000/0000`；整段处理得到两次 `rgb:cdcd/0000/0000`，分包无关性断言失败。这里用 `Theme::XTERM` 方便辨认；设置 paddock 主题后仍是同一问题。
- **改法**：在解析到查询时固定该时刻的颜色，或在不会越过后续改色／重置的边界及时消费查询事件。补一条同一字节流整体输入与分段输入得到相同回答的回归测试，包含设置、查询、重置的交错；现有测试把设置、查询和重置分开调用，抓不到这个缺陷。

### 2. 必须改：会话启动期间换主题，首次查询仍可能答旧主题

- **位置**：`app/src/viewer.rs:325–364、382–405` 的 `let theme = self.theme`；`app/src/view.rs:316–322、616–629` 的 `set_theme`／`adopt`。
- **问题**：spawn 线程捕获的是调色板副本。一个可达的顺序是：旧主题下开始接入 → worker 等待远程连接或身份查询 → 用户换主题，此时还没有 `session`，只更新了 `viewer.theme` → worker 用旧副本创建 `Screen` → 子进程立即查询背景色 → UI 才在 `adopt` 中补上新主题。查询发生在换主题之后，却仍会答旧色；程序可能据此选错深浅配色，并且不再主动查询。`adopt` 的补设只能修正后续查询，无法修正已经送出的回答。此项依据上述调用链和线程先后确认，未起真实远程会话。
- **改法**：让启动中的 worker／尚未被窗格接手的 `Screen` 也能读取当前调色板，例如共享可更新的主题状态；不能只依靠启动时复制和接手后补设。用假启动流程设置同步点：开始启动后换主题，放行子进程，让它在 UI 接手之前发 OSC 11，断言首次回答就是新主题。现有 `Screen::set_theme` 单测没有覆盖这段生命周期。

### 3. 建议改：合并的是待处理的铃，不是整帧期间的唤醒

- **位置**：`app/src/pty.rs:96–106、218–224`，`app/src/view.rs:261–269、601–605`；完成记录“做了什么”第 1 条的“最多按帧率醒，不会比原来 125 次/秒更勤”。
- **问题**：`frame_pending` 阻止再次检查 damage 和 `notify`，但接收循环仍会取走每个铃，再调用 `this.update`。容量 1 只合并尚未取走的通知；取走以后，读线程下一次读到输出又能响。因此持续输出、甚至窗格被遮住时，消费通知的次数仍可能远高于帧率。没有发现因此必然卡死，不能把它写成必须改；但当前代码不能支持完成记录中的唤醒频率保证。
- **改法**：至少修正完成记录，把“重画请求被合并”和“异步任务被唤醒”分开说明。若要兑现按帧限唤醒，应让输出通知在一帧完成前保持合并，状态变化通知仍可立即唤醒，并检查清除待处理标记时不会漏掉并发输出。用合成输出计数通知消费次数即可，不需要真实 agent 或窗口实测。

### 对“拿主意的地方”逐条表态

1. **100 ms 低频节拍：同意。** 符合任务要求，resize 和输入不靠它；退出／接入的兜底延迟可接受。空闲 CPU 降幅仍留给用户实际确认。
2. **区分输出铃与变化铃：同意。** 可避免每块输出都执行 `viewer.tick`，且状态变化仍能完整推进生命周期。
3. **一帧待画时合并后续输出，构建快照时清 damage：同意重画合并的做法。** 不同意据此宣称异步循环按帧率醒，详见建议 3；目前未发现该清除顺序永久漏画。
4. **查询回答排在已送输入之后，不插入粘贴：同意。** 与任务的顺序要求相符，一次粘贴的完整字节消息由单一写线程写完。
5. **`Session::send` 不返回 `Result`、保留 `Viewer::send` 的 `Result<bool>`：同意。** 前者符合退出后丢弃且不报错的要求，后者仍表达没有会话与暂停状态，无需恢复 busy 提示。
6. **`spawn`／`spawn_shell` 接收主题参数：同意初始化时就提供主题。** 但副本不足以保证启动期间换主题后查询正确，必须补上意见 2 的同步；完成记录中同段查询与改色的限制也不能作为例外，应按意见 1 修正。
