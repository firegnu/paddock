### 2. 为什么允许列表里的 paddock 仍可能不生效

**已查证**

```sh
codesign -dvvv -r- "$HOME/Applications/paddock.app"
plutil -p "$HOME/Applications/paddock.app/Contents/Info.plist"
codesign --verify --verbose=2 "$HOME/Applications/paddock.app"
/usr/bin/security error -67050
```

关键输出：

```text
Identifier=paddock-c93cf5ad6779a05c
flags=0x20002(adhoc,linker-signed)
Signature=adhoc
CDHash=1478c8bdf2820807f93ba2bae418a97d2d06f578
Info.plist=not bound
TeamIdentifier=not set
Sealed Resources=none
# designated => cdhash H"1478c8bdf2820807f93ba2bae418a97d2d06f578"
CFBundleIdentifier => dev.paddock.app
codesign --verify: code has no resources but signature indicates they must be present
-67050: code failed to satisfy specified code requirement(s)
```

首条日志查询里，同一次 ScreenCapture 请求还给出：

```text
21:20:30.655 ... SecStaticCodeCheckValidity() ... from dev.paddock.app :
  cdhash H"ee6e8ef8fa3f8e53444701d07617af9936abd46b"; status: -67050
21:20:30.668 ... from dev.paddock.app :
  cdhash H"ee6e8ef8fa3f8e53444701d07617af9936abd46b"; status: -67050
```

- TCC 当时比较的特定代码 hash 为 `ee6e…d46b`，本轮磁盘安装包为 `1478…f578`，两者不同；TCC 校验确实失败。日志中的另一个 `anchor apple; status: -67050` 是平台身份检查，**不能单凭它认定普通第三方 app 无权截图**。
- `app/examples/bundle.rs:14,35–40,58,73` 固定 plist 的 `dev.paddock.app`，复制 release 二进制后生成 plist、图标，再复制到安装目录；整份脚本没有 `codesign` 步骤。这解释了为什么拥有 app 外壳，但仍保留链接器对裸二进制的 ad-hoc 签名。对 app 和 `Contents/MacOS/paddock` 分别做整体验证，都得到上面的资源签名错误。
- 当前 DR 是精确 cdhash，具有“只认这一份代码”的性质。Apple 对 cdhash 要求的定义是与指定值精确匹配，程序内容变化会改变 CodeDirectory：[Code Signing Requirement Language](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/RequirementLang/RequirementLang.html#//apple_ref/doc/uid/TP40005929-CH5-SW1)。Apple DTS 也说明 ad-hoc 缺乏跨版本稳定身份：[On File System Permissions](https://developer.apple.com/forums/thread/678819)。

各因素的判断：

| 因素 | 本轮能下的结论 |
| --- | --- |
| ad-hoc／cdhash | 已确认当前 DR 绑定精确 hash，且日志实际比较了不同的 hash。旧身份要求不适配新构建是高可信解释。不能把 ad-hoc 简化成“任何时候都不能授权”。 |
| Identifier 每次变化 | 只核实了当前 signing Identifier 与 plist ID 不同；没有跨构建样本，**没证明每次都变**。即使 Identifier 不变，精确 cdhash 要求也可能失效。 |
| `Info.plist=not bound` | 已确认未绑定，且整体 app 验签失败；这是打包签名缺口。但 TCC 仍成功把路径归到 `dev.paddock.app`，不能说系统完全认不出 app，也不能单独证明此项就是截图失败的充分原因。 |
| cargo 二进制与安装 app | 源码表明测试二进制和安装路径是不同产物。权限归属取决于截图调用者的 responsible code，**不由被拍窗口属于哪个二进制决定**；上述请求实际归属安装 app，不能据此建议给每个 worktree 的 paddock 都授权。 |

**推测**：用户允许列表里的条目很可能保留了先前构建的代码身份；频繁覆盖安装加上不稳定 DR，使显示名称仍是 paddock 而实际校验不通过。安装包不完整的签名封装也可能独立影响 TCC 验证，不能把 `-67050` 全部归因于 hash 一个因素。

**不知道／权限边界**：没有核验用户当时点选的具体文件、UI 开关状态、数据库 `auth_value`、旧 hash 对应的构建时间，也没有核验运行中映像与当前磁盘文件完全一致。尝试用 `sqlite3 -readonly` 对系统 TCC.db **仅查询 ScreenCapture 且 client 匹配 paddock/corral/codex/screencapture 的行**，得到 `authorization denied`，没有读出任何行；`launchctl procinfo 69778` 返回 `requires root privileges`。到此停止这些受保护检查，没有 sudo、换权限重试或修改数据库。独立 `codesign` 指定旧 hash 的验证在纠正参数语法后仍先失败于资源封装，故不把它当作“单独隔离 hash 因素”的实验。

### 3. 有没有可能是窗口或 macOS 行为问题

**已查证**

- `app/src/main.rs:210` 调用 `windows::announce`；真正打印 ID 的代码现在位于 `app/src/windows.rs:267–285`，通过 GPUI 的 AppKit `NSView → NSWindow → windowNumber` 取得原生窗口编号，不是 GPUI 内部实体编号。
- `app/src/main.rs:218–222` 中 `PADDOCK_NO_ACTIVATE` 只控制是否调用 `cx.activate(true)`，该分支没有截屏授权操作。
- 本机 `/usr/sbin/screencapture -h` 仍明确列出 `-l<windowid> capture this windowsid` 和 `-o` 去阴影。只运行了帮助，没有捕获图像；这证明参数仍存在，不能证明 macOS 27 在所有窗口状态下的实现行为不变。
- `docs/原型实测记录.md` 的历史记录说明完全遮挡会让 GPUI 暂停重绘；它记录的是旧帧现象，不是本轮的新窗口状态实测。

**推测**：当前优先级是身份／授权校验，其次才是窗口 ID 已失效、窗口未准备好或不可捕获，再其次是 macOS 27 的接口回归。窗口状态问题可以解释取不到图像，但不能解释已观察到的 TCC 签名要求失败；遮挡导致旧帧也不能直接等同于 `could not create image from window`。

**不知道**：历史截图的窗口是否仍存活、是否在当前 Space、是否被最小化或完全遮挡，以及第一次绘制是否完成。本轮没有启动测试窗口、枚举其他窗口、截图或修改激活条件，因而没有排除并存的窗口问题，也没有复现该 stderr。未取得同一请求可明确解读的最终 ScreenCapture 拒绝码；日志中的 `Unknown (None)` 只按原义记录，不冒充明确的用户拒绝。不会把上下文未对应好的 `result=false` 当成证据。
