# P5-19：在 GPUI 窗口中接入 macOS 液态玻璃

调研日期：2026-10-06。任务：[P5-19r](../任务/P5-19r-液态玻璃调研.md)。调查基线：paddock `6e899d660507d4a85ddbe73b66601ae78d4ebc5a`，`gpui-pre-* =0.3.8`，上游 GPUI 快照 `279fe070bb389b79652e52065b2f001edcc0b11b`。本机 macOS 27.0.1、当前 Xcode SDK 27.0；没有安装或升级组件。

标记含义：**【已查证】**是本轮读到的官方文档、SDK 头文件或固定版本源码；**【推测】**是据此作出的工程判断、建议或估算；**【未知】**是尚无运行证据的部分。源码可行不等于视觉验收通过。本轮没有写试验代码、编译、启动窗口或截图。

## 结论先行

- **【已查证】可以从 paddock 经公开接口取得 GPUI 的原生 NSView，再取得 NSWindow 和窗口 contentView。**已有 `app/src/windows.rs:269–287` 的 `announce` 已沿这条链路取得 NSWindow；contentView 的读取见 GPUI 实现（G1）。无需 fork GPUI，也不需要访问其私有 Rust 字段。
- **【推测】在该 NSView 后面插入局部原生玻璃视图，并同步侧栏矩形，机械上可行；【未知】这样能否稳定得到用户想要的液态玻璃。**Apple 明确建议不要把玻璃作为内容后面的兄弟视图，内容应交给玻璃的 `contentView`。这是本方案的主要限制，不能把“能拿到指针”写成“原生侧栏已经可用”。依据见 §1、§2。
- **【已查证】当前侧栏与终端共用一个 GPUI 原生绘制视图；【推测】把整个绘制视图放进玻璃 contentView 也不能直接得到独立侧栏的玻璃边缘。**符合 Apple 推荐层级的局部方案需要进一步研究内容拆分，代价明显大于加一层透明底色。
- **【推测／建议】维持 DESIGN §13 的次序：先做 P5-19a 毛玻璃实窗体验；原生玻璃只作为另行批准的小试验。**本轮没有证明原生接入做不到，也没有证明它满足生产使用要求。继续原生方向前，由主控把本结论交用户决定。

## 1. Apple 的公开接口、用法与限制

### 1.1 接口与版本

**【已查证】**以下声明来自本机 SDK 的 `AppKit.framework/Headers/NSGlassEffectView.h`，在线类文档的 availability 同样为 macOS 26.0 起：

| 接口 | 用途与版本 | 直接依据 |
| --- | --- | --- |
| `NSGlassEffectView : NSView` | macOS 26.0 起；`contentView`、`cornerRadius`、`tintColor`、`style` | 头文件 14–37 行；[Apple 类文档](https://developer.apple.com/documentation/appkit/nsglasseffectview) |
| `NSGlassEffectViewStyleRegular` / `Clear` | 标准、清透两种风格，macOS 26.0 起；不是可任意指定的模糊半径或折射率 | 同文件 14–19、36–37 行 |
| `NSGlassEffectContainerView : NSView` | macOS 26.0 起；以 `contentView` 承载多个玻璃后代，用 `spacing` 控制接近时的融合；可合批，单个面板不必引入 | 同文件 49–65 行；[Apple 容器文档](https://developer.apple.com/documentation/appkit/nsglasseffectcontainerview) |
| `effectIsInteractive` | **macOS 27.0 起**的额外属性，默认关闭；不能误写成 macOS 26 的共同能力 | 同文件 39–45 行；不作为本任务接入前提 |

**【已查证】**容器的 `spacing` 默认 0，此时仍可合批，不要求开启相邻形状融合；容器会调整 contentView 后代的层级。它不是将任意 GPUI 图形自动变成玻璃的包装器（头文件 54–65 行）。

**【已查证】**另一个系统方案是 `NSSplitViewController` 的 sidebar / inspector 项自动采用玻璃；`NSBackgroundExtensionView` 用于把内容外观延展到安全区域外，并非玻璃本身。它们见 [WWDC25 AppKit 讲解的 App structure 部分](https://developer.apple.com/videos/play/wwdc2025/310/?time=83)。**【推测】**paddock 当前侧栏是 GPUI 元素，不能仅加一个属性就得到原生 split view 的效果；改成这套结构属于更大的设计变更，本轮不建议展开。

### 1.2 视图层级与窗口、图层要求

**【已查证】**玻璃是实际 `NSView`，应加入窗口的视图层级。Apple 保证玻璃的 `contentView` 位于效果之内；任意直接子视图与内容、玻璃之间的具体层级不作同样保证（头文件 25–28 行）。[WWDC25 Glass 部分](https://developer.apple.com/videos/play/wwdc2025/310/?time=1050)进一步明确：应设置 `contentView`，避免把玻璃放在内容后面作为兄弟视图，以便系统处理内容随玻璃变化的可读性；玻璃和 contentView 的几何通过 Auto Layout 联系起来。原文关键一句（视频文字稿）：

> So avoid placing the NSGlassEffectView behind your content as a sibling view.

**【已查证】**[NSView 的 `addSubview:positioned:relativeTo:`](https://developer.apple.com/documentation/appkit/nsview/addsubview(_:positioned:relativeto:))允许把一个视图插到另一个视图之前或之后。**【推测】**因此“放在 GPUI 后面”在普通 AppKit 层级操作上并未被禁止；但这不覆盖前述玻璃内容适配约定，不能称为 Apple 推荐的玻璃用法。

**【已查证】**已检查的玻璃头文件和类文档没有要求使用某种专用 NSWindow 子类，也没有暴露自定义 Metal shader、背景采样源、模糊半径或 `NSVisualEffectView.blendingMode` 一类的开关。不要把缺少声明理解为任意混合渲染方式都受保证。

**【已查证】**GPUI 原生视图本身是 layer-backed，`makeBackingLayer` 返回其渲染器的层；本配置走 Metal 渲染路径（G1、G3）。**【推测】**接入时保留它的层、delegate、first responder 和事件路径，仅管理新增视图；不要替换 CAMetalLayer、操作系统内部玻璃图层或调用私有过滤器。

**【推测】**若要透出窗口外背景，窗口和覆盖区域的渲染层需要允许透明；但“NSGlassEffectView 无论如何都要求整个窗口透明”不是本轮查到的通用规则，窗口内内容也可以作为玻璃背后的画面。**【未知】**局部玻璃与 GPUI Metal 层相邻时实际采样哪些内容、能否得到窗口外背景以及系统如何调节外观，需要实窗验证。不能凭 `Transparent` 的名字作保证。

## 2. 不改 GPUI，能拿到什么、能接到哪一步

### 2.1 已存在的公开通路

**【已查证】**固定版本的链路如下（G1、G2、P1、R1）：

```text
gpui::Window
  → raw_window_handle::HasWindowHandle::window_handle(window)
  → RawWindowHandle::AppKit(handle).ns_view
  → [ns_view window] → NSWindow → [window contentView]
```

必须显式调用 trait 方法：GPUI 另有同名固有方法 `Window::window_handle()`，返回的是 GPUI 的 `AnyWindowHandle`，不是原生句柄。原生句柄返回的是 **GPUI 绘制 NSView，而非 NSWindow，也非窗口 contentView**。操作限于主线程及窗口有效期；裸指针不是所有权转移。

**【已查证】**`gpui-pre-macos` 的 `MacWindow::new` 创建 GPUI native_view 后，将其加为窗口 contentView 的子视图，设置宽高 autoresizing，并令其成为 first responder。当前结构为：

```text
NSWindow
└─ 系统 contentView
   ├─ BlurredView（仅 Blurred 模式，位于底部）
   └─ GPUI native_view / 渲染层（整个窗口的 GPUI 场景）
      └─ 侧栏、标题栏、终端等是绘制元素，不是各自的 NSView
```

依据：G1 `window.rs:1085–1197`、`1857–1895`；P2 `PaddockWindow::render`。

### 2.2 三种接法的判断

| 接法 | 能否不改 GPUI 源码 | 判断与代价 |
| --- | --- | --- |
| 在 GPUI native_view 的同一父视图中，插入侧栏大小的玻璃兄弟视图，排在其后 | **【推测】可以完成插入和矩形同步**：公开原生句柄＋AppKit 方法足够 | **【未知】视觉正确性和系统适配**；偏离 Apple 对 contentView 的推荐。适合作为受限试验，不能当成已完成的产品方案 |
| 将整个 GPUI native_view 设为玻璃 contentView，玻璃铺满窗口，终端仍画不透明 | **【推测】可以尝试重挂视图，但无 GPUI 兼容性保证** | 玻璃轮廓变为整窗；遮住右半边不能自然变出侧栏右边缘的折射／圆角。重挂还会改变父视图与 responder 链，风险更高 |
| 让侧栏本身成为独立原生内容视图，再作为局部玻璃 contentView | **【已查证】当前代码没有这个独立 NSView** | **【推测】**需要新增嵌入渲染能力或原生侧栏结构，不能把现有 GPUI `Div` 强转成 NSView。**【未知】**在“不改 GPUI”约束下是否能以合理成本做到；本轮不承诺工期 |

**【推测】**第一种若另立试验，最小做法是：在主线程探测玻璃类是否存在，取得 native_view 的实际父视图，创建并保留单个玻璃实例，调用 `addSubview:positioned:relativeTo:` 将它放在 native_view 后；随后仅更新 frame、隐藏状态和外观，退出时移除并释放自己拥有的视图。不要每帧重建实例，也不要把 GPUI 的绘制视图缩到侧栏大小。Apple 文档说明父视图会 retain 子视图，移除时 release；Rust 一侧仍需明确自己的持有关系（A3）。

### 2.3 拖宽、收起、缩放、全屏如何同步

下列是**【推测】实现办法，未运行验证**；每项所需的输入接口已查证：

| 变化 | 建议的同步来源 | 已查证依据 |
| --- | --- | --- |
| 拖宽 | 使用实际绘制宽度持续更新，不只读保存后的配置 | P2 `resize_sidebar:835–847` 更新内存宽度并通知重画 |
| 收起／展开、字号变化 | 复用 `sidebar_shown`；收起后是按界面字号缩放的窄条，不能一律设成隐藏或硬编码 52pt | P2 `sidebar_shown:794–801` |
| 窗口缩放 | 观察窗口 bounds，加上布局完成后取得的侧栏真实 Bounds | G2 `Context::observe_window_bounds:401–417`、`canvas` 的 prepaint／paint Bounds 参数 |
| 全屏及恢复 | 遵照 DESIGN §13，进入全屏隐藏玻璃并恢复不透明底色；退出后按新 bounds 重算，标题栏红绿灯布局也需重算 | P2 渲染读取全屏状态；G1 全屏 bounds／resize 路径；策略来自 DESIGN，而非 Apple 禁止全屏玻璃 |
| 移到另一缩放比例的屏幕 | 按当前逻辑坐标更新；核对像素对齐，不把尺寸再次乘 Retina 倍率 | G1 `set_frame_size:3253–3289` 将 NSSize 直接变为 GPUI Pixels，另乘 scale_factor 更新 drawable；G2 `Window::scale_factor` |

**【推测】**用占据侧栏目标区域的 GPUI `canvas` / 自定义元素取得最终布局矩形，比只依赖窗口 resize 通知可靠：拖侧栏不会必然改变窗口尺寸，标题栏高度也受字号与宠物影响。若需延后 AppKit 更新，利用 GPUI 的前台回调，但不能假定 `on_next_frame` 与 Metal 呈现同一事务；一帧滞后、隐式动画需另查。

**【已查证】**AppKit 提供 `isFlipped` 和 `convertRect:toView:`（A2）。**【推测】**先把 GPUI 左上原点矩形转换为源 NSView 本地坐标，再转到新增视图的父视图坐标；未翻转且 bounds 原点为零时，纵向换算为 `y_native = H - y_gpui - h`。不要把窗口屏幕坐标当内容坐标，也不要无条件假设 native_view 是 flipped。

**【未知】**全屏动画中层级是否保持、快速缩放是否错帧、窗口恢复与多窗口释放是否安全，尚无实测。公开句柄只保证访问路径，不承诺第三方重组视图树后 GPUI 的所有假设仍成立。尤其 G1 `content_size:933–937` 读取窗口 contentView 尺寸，而不是任意新父视图尺寸。

## 3. GPUI 怎样透出玻璃，与 Blurred 是否冲突

### 3.1 透明链路

**【已查证】**`Window::set_background_appearance` 是公开方法；`WindowOptions.window_background` 可设置初始模式。macOS 实现中：

- `Opaque` 令 NSWindow opaque、渲染器 opaque，窗口底色 alpha 为 1。
- `Transparent` 和 `Blurred` 都令 NSWindow 与 Metal 层允许透明；窗口底色 alpha 为 0.0001（源码注明为避免阴影损坏，并非直接 clearColor）。
- Metal 渲染器在非 opaque 时以 alpha 0 清屏。`Transparent` 同时移除 GPUI 自己建立的 BlurredView；`Blurred` 则在窗口 contentView 底部放一个全尺寸 BlurredView。

依据：G1 `1857–1895`，G2 `2941–2944`、`platform.rs:2710–2730`，G3 `463–468`、`703–711`。

**【推测／建议】**试原生玻璃时使用 `Transparent`，使玻璃成为该区域唯一的系统材质；用 GPUI 的公开方法保持窗口与渲染器状态一致，不单独改 `NSWindow.opaque`。仅改窗口透明不够：当前 P2 根元素 `window.rs:3782` 的 `agents_bg` 是 alpha 1，会覆盖整窗，侧栏自身和选中块也有不透明填充（P3）。

**【推测】**应让根背景在目标矩形内不盖住玻璃，侧栏、标题栏相关背景用 alpha 0 或适度半透明；右侧终端卡片保持 alpha 1，非玻璃区域的缝隙另画所需底色。先用完全透明目标区域确认材质，再按三套主题调节着色覆盖。没有一个由接口推出的“最佳透明度”数值，需用户看实窗。

**【推测】**只降低背景填充的 alpha，不降低整个侧栏视图的 opacity，否则文字、图标也一起变淡。前景的亮暗适配仍由 paddock 主题处理；把系统玻璃放在 GPUI 后面不会自动把 GPUI 字形变成 AppKit 可适配的原生标签。

### 3.2 和现成 Blurred 的关系

**【已查证】**Blurred 不是 NSGlassEffectView：固定版本创建 NSVisualEffectView 子类，用 Selection material 和 Active state，并在 `updateLayer` 里修改其内部背景、染色及饱和度相关层（G1 `3776–3837`）。因此它也不是系统默认 sidebar glass。不要把 GPUI 针对 BlurredView 的内部处理复制到玻璃视图。

**【推测】**Blurred 与另插的玻璃不会因为类名相同而冲突，但会有两层材质参与合成，可能改变采样、透明感和开销；GPUI 切换模式还会插入／移除它自己的 blur 层。**【未知】**实际结果是否失真未测，不应宣称两者叠加必然更好或必然崩溃。原生试验采用 Transparent；退回现成毛玻璃时移除自建玻璃，再切到 Blurred。

**【已查证】**DESIGN §13 已规定全屏退回不透明。**【推测】**减少透明度、提高对比度等系统辅助功能，以及前后台窗口外观，后续落地也需观察；目前没有证据说明系统会替 GPUI 自绘文字完成这些适配。

## 4. Rust 库、版本与共存

**【已查证】**当前 `app/Cargo.toml` 已直接声明 `raw-window-handle = "0.6"`、`objc2 = "0.6"`；锁定分别为 0.6.2、0.6.4。`objc2-app-kit 0.3.2`、`objc2-foundation 0.3.2`、`objc2-core-foundation 0.3.2` 已在锁文件中，由 GPUI 等传递引入。不是必须升级 GPUI 才有玻璃声明。

| 选择 | 所需库与版本 | 判断 |
| --- | --- | --- |
| 少量动态消息调用 | 现有 `objc2 0.6.4`、`raw-window-handle 0.6.2` | **【推测】**可不增加新的直接库，用运行时类查找与消息调用；代价是自己核对 selector、ABI、结构体布局、retain/release 和可用性，正式维护容易出错 |
| 类型化 AppKit 桥接，建议给后续试验选用 | 直接声明现有版本 `objc2-app-kit =0.3.2`、按实际类型使用声明 `objc2-foundation =0.3.2`；几何等需要时才直接声明 `objc2-core-foundation =0.3.2` | **【已查证】**0.3.2 生成绑定已含 NSGlassEffectView 和 NSGlassEffectContainerView；**【推测】**更适合管理类型与所有权。仅列候选，本轮不改清单／锁文件 |

**【已查证】**AppKit 0.3.2 的 `NSGlassEffectView` feature 覆盖这两个类；还涉及 `NSView`、`NSResponder`、`NSWindow`、`objc2-core-foundation`，用 tint 时需 `NSColor`。GPUI 的 AppKit 依赖关闭 default features，列出的功能中没有 `NSGlassEffectView`，不能把“锁文件有库”当作 paddock 已可直接 import 全部接口。依据：B1 `Cargo.toml:681–686`、生成文件 `NSGlassEffectView.rs:35–41,95–153,190–198`；G1 清单 `156–179`。

**【已查证】**该库要求 `objc2 >=0.6.2, <0.8.0`，与当前 0.6.4 兼容；Rust 最低版本声明为 1.71，低于本项目要求的 1.96。许可为 `Zlib OR Apache-2.0 OR MIT`。锁文件同时已有老 `objc 0.2.7`、`objc2 0.5.2` 和 AppKit 0.2.2；GPUI macOS 后端自身也混用旧 `objc` 和新 `objc2`。

**【推测】**选择同一个 0.3.2 可复用当前新版本依赖，不需要为了玻璃升级或清理旧依赖。它们共享系统 Objective-C runtime，并不因为同时存在就天然冲突；风险在 Rust 类型和所有权边界：不同版本的 `Retained`／对象引用不可随意互换，原生句柄转换应封装成窄桥接。实际 feature 合并和链接仍需未来编译确认，本轮未运行 Cargo。

**【已查证】**维护主体是 [madsmtm/objc2](https://github.com/madsmtm/objc2)。本轮 GitHub API 返回仓库未归档，最近推送时间为 `2026-10-05T18:35:25Z`，最近提交 [`78216adc`](https://github.com/madsmtm/objc2/commit/78216adc63fd8616cdfe0360ec628dc54a3fa9f4)内容为合入 objc2 0.6.5 的版本与变更记录。**【推测】**可认定项目仍活跃，但维护活跃不保证本桥接场景正确。crates.io API 本轮返回 HTTP 403，因此不宣称 0.3.2 是最新版本；它是已锁定且确认含所需接口的候选。未建议升级 objc2。

**【推测】**若保留 macOS 26 以前系统的运行能力，创建前需系统版本／类存在性检查，失败回退 Blurred 或不透明；已有 `objc2::runtime::AnyClass::get` 可探测类（B2）。绑定能编译不意味着旧系统有该类。27 专属 `effectIsInteractive` 不在当前 0.3.2 的上述绑定中，本路线也不需要它。

## 5. 推荐、工作量、风险和可接近的程度

以下均为**【推测／建议】**，不是新增验收条件、批准的设计或已实施工作。估算按一名熟悉仓库的开发者计，不含等待用户体验：

| 路线 | 粗估工作量 | 得到什么／主要风险 |
| --- | --- | --- |
| 继续 P5-19a，GPUI Blurred＋透明底色，随后调浮动圆角和细高光 | 小，约 0.5–1.5 个工作日，取决于三主题调色 | 能有真正的窗口后背景模糊，以及 GPUI 画出的浮动边框和高光；保留现有 GPUI 内容与事件结构 |
| 局部原生玻璃兄弟视图试验 | 约 0.5–1 个工作日，先回答视觉合成是否值得继续 | 验证是否有可见原生材质及跟随几何；仍偏离 contentView 推荐用法，不可把试验时长当交付估算 |
| 试验成立后的生命周期、全屏、主题、输入与系统设置整合 | 另约 2–4 个工作日，低置信度 | 可能因材质采样、错帧或前景适配失败而停止；尚无实测，不能承诺达到产品质量 |
| 把侧栏做成独立原生内容／嵌入式 GPUI 渲染面 | 明显更大，当前证据不足以估工期 | 涉及渲染和事件结构变更，需要独立设计与用户决定，不作为 P5-19a 的顺带改动 |

**【已查证】**GPUI 当前提供圆角、边框、阴影绘制；`style.rs` 中的 `blur_radius` 是阴影模糊，不能当成通用背景滤镜。`WindowBackgroundAppearance::Blurred` 才是此版本现成的窗口后背景模糊入口（G2、G4）。

**【推测】**用浮动圆角面板、半透明主题底色、细亮边和软阴影，可以接近玻璃的轮廓、层次和透感；配合 Blurred 能有真实毛玻璃。单靠这些 GPUI 绘制不能等同于系统液态玻璃的动态折射、随背景变化的高光和相邻玻璃融合，本轮也没有找到一个公开的 GPUI 材质 API 能直接提供这些能力。不要用“阴影有 blur”推导“能做 backdrop blur”。

**【未知】待决定原生试验后才验证：**Metal 与玻璃采样、侧栏边缘是否正确、连续拖宽和窗口缩放是否错帧、全屏进出／显示器缩放切换、遮挡后恢复、主题及辅助功能下文字可读性、终端输入焦点／IME／拖放、退出释放与 GPU 开销。本轮静态调查足以判断公开访问通路，**不足以批准产品级原生接入**。按任务限制没有自行增加运行测试或系统交互。

**主控需要决定的事：**向用户展示结论，是否在 P5-19a 之外另开原生玻璃试验；若开，以验证可行性为目标，把 contentView 层级限制列为停止／继续的判断依据。没有需要主控批准后本轮才能完成的事项。
